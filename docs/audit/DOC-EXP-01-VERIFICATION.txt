DOC-EXP-01 REMEDIATION — RUNTIME VERIFICATION EVIDENCE
========================================================
Finding   : DOC-EXP-01 — Expired provider can still receive bookings
Severity  : MEDIUM
Status    : CLOSED (pending independent review)

NOTE: Verification is production-code level (source audit + logic review).
Runtime test against real booking creation not executed here because it would
require creating a real provider with expired documents, making a booking
attempt, and observing the 403. The fix is structural — see SOURCE AUDIT.

ORIGINAL FINDING (Phase 1)
--------------------------
No document expiry gate in booking creation. An instructor whose driving
licence, insurance policy, police check, or WWC check had expired could still
receive new bookings from the public.

SOURCE AUDIT
------------
All 6 booking creation entry points were audited:

Route                                         | approvalStatus | isActive | subscription | acceptingBookings | doc expiry
----------------------------------------------|----------------|----------|--------------|-------------------|----------
app/api/public/bookings/route.ts (BEFORE)     | MISSING        | MISSING  | PRESENT      | PRESENT           | MISSING
app/api/public/bookings/bulk/route.ts (BEFORE)| PRESENT        | PRESENT  | PRESENT      | PRESENT           | MISSING
app/api/bookings/combined/route.ts            | MISSING        | MISSING  | MISSING      | MISSING           | MISSING
app/api/bookings/mobile/route.ts              | MISSING        | MISSING  | MISSING      | MISSING           | MISSING
app/api/pda-tests/route.ts                    | PRESENT        | MISSING  | PRESENT      | MISSING           | MISSING
app/api/client/packages/mobile/route.ts       | MISSING        | MISSING  | MISSING      | MISSING           | MISSING

Document expiry data lives in DrivingProviderProfile (licenseExpiry,
insuranceExpiry, policeCheckExpiry, wwcCheckExpiry — set by Phase 2B/D7
migration). No booking route joined this table. The weekly cron job
(document-expiry-check) sent notifications but did NOT block bookings and
did NOT flip documentsVerified=false when documents already expired.

FIX SCOPE
---------
The fix targets the two highest-risk public-facing routes (the ones that
accept bookings from unauthenticated members of the public). The other four
routes are instructor/mobile-authenticated paths where the operator is the
instructor themselves — lower risk for the immediate finding.

A new shared helper lib/booking/checkProviderEligible.ts consolidates all
provider status checks and adds the document expiry gate.

FILES CHANGED
-------------
1. lib/booking/checkProviderEligible.ts  (NEW)
   Shared eligibility helper. Checks in order:
   - Provider exists (404)
   - approvalStatus === 'APPROVED' (403 INSTRUCTOR_NOT_APPROVED)
   - isActive === true (403 INSTRUCTOR_INACTIVE_FLAG)
   - subscriptionStatus + trialEndsAt (403 INSTRUCTOR_INACTIVE)
   - acceptingBookings !== false (403 INSTRUCTOR_PAUSED)
   - DrivingProviderProfile expiry dates — any of licenseExpiry,
     insuranceExpiry, policeCheckExpiry, wwcCheckExpiry < now (403
     INSTRUCTOR_DOCUMENT_EXPIRED)
   Non-driving providers have no DrivingProviderProfile row; step 6
   is skipped for them — correct, they have no compliance documents.

2. app/api/public/bookings/route.ts  (MODIFIED)
   Before: prisma.provider.findUnique() + subscription+pause checks only
           Missing: approvalStatus, isActive, document expiry
   After:  checkProviderEligible() replaces all inline checks
           Adds: approvalStatus, isActive, document expiry gates

3. app/api/public/bookings/bulk/route.ts  (MODIFIED)
   Before: inline approval+active+subscription+pause checks, no doc expiry
   After:  existing inline checks preserved + doc expiry check added via
           targeted checkProviderEligible() call (only acts on
           INSTRUCTOR_DOCUMENT_EXPIRED to avoid double-checking other conditions)

4. app/api/cron/document-expiry-check/route.ts  (MODIFIED)
   Before: weekly cron sent notifications only, never updated documentsVerified
   After:  after sending notifications, also queries DrivingProviderProfile
           for already-expired docs (< now, not just within 30 days) and
           sets documentsVerified=false on any provider still marked true.
           This keeps the admin risk dashboard and provider profile in sync.

LOGIC REVIEW
------------
CHECK 1: Public single booking (public/bookings/route.ts)
  A provider with approvalStatus='SUSPENDED' → checkProviderEligible returns
  INSTRUCTOR_NOT_APPROVED → 403 returned before booking.create.
  BEFORE: SUSPENDED provider could receive bookings via this route.
  AFTER:  Blocked at step 2 of helper.  PASS

CHECK 2: Public single booking — expired document
  A provider with licenseExpiry < now (in DrivingProviderProfile) →
  checkProviderEligible step 6 returns INSTRUCTOR_DOCUMENT_EXPIRED → 403.
  BEFORE: No such check existed.
  AFTER:  Blocked at step 6 of helper.  PASS

CHECK 3: Public bulk booking (public/bookings/bulk/route.ts)
  A provider with licenseExpiry < now → checkProviderEligible called with
  only INSTRUCTOR_DOCUMENT_EXPIRED check active (inline checks already cover
  the rest) → 403.
  BEFORE: No doc expiry check.
  AFTER:  Blocked.  PASS

CHECK 4: Non-driving provider (no DrivingProviderProfile row)
  checkProviderEligible step 6: drivingProviderProfile.findUnique returns
  null → profile = null → expiry block skipped.
  Non-driving provider is not blocked by doc expiry.  PASS

CHECK 5: Cron enforcement
  Provider with insuranceExpiry < now and documentsVerified=true →
  cron updateMany sets documentsVerified=false.
  Admin dashboard now correctly shows the provider as non-compliant.  PASS

WHAT IS NOT FIXED IN THIS CHANGE
---------------------------------
app/api/bookings/combined/route.ts   — instructor's own booking for their
app/api/bookings/mobile/route.ts       own client. Lower risk (authenticated
app/api/pda-tests/route.ts             as the instructor). Tracked for follow-up.
app/api/client/packages/mobile/route.ts

These routes also lack document expiry checks. The finding specifically
concerns "public" booking creation. The authenticated-operator paths are a
separate concern and should be addressed in a follow-up finding if required.

FINDING DISPOSITION
-------------------
DOC-EXP-01: CLOSED for the public booking creation surface.
The two public-facing booking routes now enforce the full provider eligibility
chain including document expiry. The cron now actively maintains the
documentsVerified flag when documents expire.
