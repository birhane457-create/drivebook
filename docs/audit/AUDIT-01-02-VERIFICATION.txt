AUDIT-01 / AUDIT-02 REMEDIATION — VERIFICATION EVIDENCE
=========================================================
Findings  : AUDIT-01 (audit logging fails open) + AUDIT-02 (not atomic with state change)
Severity  : MEDIUM (both)
Status    : CLOSED

NOTE: Verification is source-audit + unit test level (no Docker required for unit tests).
Runtime hostile tests require the test DB and are not included in this evidence set.

ORIGINAL FINDINGS
-----------------
AUDIT-01: lib/services/auditLogger.ts logAuditEvent() catch block explicitly swallows
failures — "Don't throw - we don't want to break the main operation." This means every
call site that uses logAuditEvent() (or any wrapper: logBookingAction, logFinancialAction,
logSubscriptionAction) has silent audit failure with no propagation.

AUDIT-02: logAuditEvent() accepts no transaction client parameter. Every call site that
mutates state inside a $transaction and then calls logAuditEvent() outside the transaction
has a non-atomic audit write. Wallet debits, booking confirmations, subscription overrides,
and Stripe webhook handlers all had this pattern.

An existing correct implementation existed in lib/services/audit.ts (logAuditAction(tx))
but was never imported anywhere in the codebase.

REMEDIATION DESIGN
------------------
Rather than changing logAuditEvent() globally (which would break legitimate
non-critical callers), the fix is tiered per operation type:

Tier 1/2/3 — writeAuditLog(tx, data)
  New function in lib/services/audit.ts. Requires a Prisma transaction client.
  Writes via tx.auditLog.create(). If the write fails, the error propagates
  and the caller's $transaction rolls back — state change never commits without
  its audit record. Never catches errors.

Tier 4 — writeAuditLogSafe(data)
  New function in lib/services/audit.ts. Uses module-level prisma (no tx).
  Does NOT throw on failure. Logs at ERROR level with explicit documentation
  that this specific call site has been reviewed and accepts non-atomic
  audit failure. Replaces silent catch blocks.

F09 COMPATIBILITY
-----------------
F09 explicitly treated audit logs as non-critical inside webhook transactions.
The Tier 3 fix replaces this with atomicity:
  - On serialization retry (P2034), the audit write now rolls back with the tx
  - The retry re-writes the audit entry — exactly once, no duplicates
  - The idempotency key (also inside the same $transaction) prevents double-processing
  - No duplicate financial state from retries

app/api/stripe/webhook/__tests__/f09-retry.test.ts updated to reflect
that audit logs are now atomic on retry (previously documented as a
"known trade-off" for duplicate audit entries on P2034 retry).

FINDING DISPOSITION
-------------------
AUDIT-01: CLOSED. The swallowing catch in logAuditEvent() is replaced by:
  - writeAuditLog (throws, used for all critical paths)
  - writeAuditLogSafe (explicit non-throwing with ERROR-level log, used only
    where the failure policy has been reviewed and documented)

AUDIT-02: CLOSED. All Tier 1/2/3 critical call sites now write the audit
entry inside the same Prisma $transaction as the state change. If the audit
write fails, the transaction rolls back and the state change is not committed.
