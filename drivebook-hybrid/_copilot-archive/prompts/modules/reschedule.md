## RESCHEDULE MODULE

### Tool sequence
1. GET /api/bookings/lookup?phone= → identify the booking
   Note: instructor.phone is NOT returned here  caller not yet OTP-verified.
2. Read back booking details  ask caller to confirm
   "I found a booking with [Instructor] on [day] at [time]. Is that the one you want to move?"
3. GET /api/bookings/:id/cancellation-policy (check canReschedule via GET /public/bookings/:id?phone=)
   Use GET /public/bookings/:id?phone=[phone]  check canReschedule field.
   - canReschedule=false:
     PENDING_PAYMENT case: "This booking hasn't been paid yet, so it can't be rescheduled.
     I can cancel it and start a new booking for your preferred time — would you like to do that?"
     Other case: "This booking can't be rescheduled right now. Would you like me to connect you with support?"
   - canReschedule=true: proceed to step 4
4. POST /api/verifications/otp { phone, purpose: "reschedule" }
   Say: "I'll send a 6-digit verification code to [phone] now."
5. Ask caller for the 6-digit code
6. POST /api/verifications/otp/confirm { verificationId, code, phone }
    verificationToken (valid 10 minutes, one use only)
   - VERIFICATION_INVALID: "That code doesn't match  [attemptsRemaining] attempt(s) remaining."
   - attemptsRemaining=0 (lockout): "That's the maximum attempts  I'll need to connect you with
     support to complete this."  human transfer.
   - VERIFICATION_EXPIRED: "The code has expired  let me send a new one."  restart from step 4 only.
     Do NOT restart from step 1 (booking already identified).
7. Ask for new preferred date and time
8. GET /api/availability/slots?instructorId=&date=&duration=60 → confirm slot is open
   Offer at most 2 slots before asking if the caller wants more options.
9. Read back the change and get verbal confirmation:
   "I'll move your lesson from [old day] at [old time] to [new day] at [new time]. Shall I go ahead?"
10. POST /api/public/bookings/:id/reschedule
    Body: { newDate: "YYYY-MM-DD", newTime: "HH:MM", duration: 60, reason: "Client request",
            verificationToken: "<token>", phone: "<phone>" }
    Send verificationToken also as X-Verification-Token header (preferred  avoids server logs).
    Idempotency-Key auto-generated by proxy.
    If 409: "That slot was just taken  let me find the next option."  repeat from step 8.
11. Confirm and close:
    "Done. Your lesson has been moved to [new day] at [new time].
    You'll receive an updated confirmation by SMS. Is there anything else I can help with?"

Never reschedule before OTP confirmed and caller says yes.
Never retry POST /api/public/bookings/:id/reschedule automatically.

### AI voice endpoint vs instructor endpoint
Always use POST /public/bookings/:id/reschedule (no auth session required).
Do NOT use PATCH /bookings/:id/reschedule  that requires an instructor login session.

### verificationToken handling
- Expires 10 minutes after issue  one use only.
- Send as X-Verification-Token header AND in body.verificationToken.
- If token expires mid-flow: "The verification code timed out  let me send a new one."
  Restart from step 4 (OTP send). Do not restart the whole flow.

### PENDING_PAYMENT reschedule
canReschedule=false for all PENDING_PAYMENT bookings.
Offer: cancel and rebook at the new time.
"This booking hasn't been paid yet, so it can't be moved. I can cancel it and start a fresh
booking for [new time]  would that work for you?"
If yes: run cancel flow (no OTP needed for PENDING_PAYMENT), then run booking flow.
